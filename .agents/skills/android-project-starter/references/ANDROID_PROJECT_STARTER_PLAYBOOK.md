# Старт Android-проекта: agent skills и проверенные UI-паттерны

Этот справочник — техническая памятка для **нового** Android-приложения на Kotlin, Jetpack Compose и Material 3. Источник практических решений — [Android Handbook Audio](https://github.com/khodorkin-dmitrii/android-handbook-audio). Ссылки на код ниже закреплены на коммите `f93c5c796a88d237c27c8c08fca2f91d8b4e5d16`, чтобы при развитии проекта примеры не менялись незаметно.

Это не шаблон для побайтового копирования. Переносить стоит **идею и контракт компонента**; цвета, размеры, навигационные ключи, доменные состояния и сложность анимаций нужно подбирать под новое приложение. В частности, Media3, плеер, транскрипты и фоновая линия прогресса нужны только медиа-продукту.

## 1. Первый день проекта

1. Создать Android-проект и проверить базовую сборку. Для Compose-приложения договориться об одной точке входа Activity, теме, навигации и владельце глобального состояния. Не добавлять «на вырост» модули, абстракции и библиотеки.
2. Положить в корень `AGENTS.md` с **правилами именно нового проекта**: цель и границы продукта, стек, структура, команды проверки, правила тестов, устройство/профили при деплое, запрет на коммит без запроса. Не копировать продуктовые требования Handbook Audio. В исходном репозитории `AGENTS.md` локален и исключён из Git — если правила должны разделять все участники нового проекта, **не игнорировать** новый `AGENTS.md`.
3. Установить [Android CLI](https://developer.android.com/tools/agents/android-cli) по инструкции для своей ОС; проверить `android --version`. Не закреплять здесь версию как обязательную: CLI и каталог skills обновляются.
4. В корне нового проекта выполнить команды ниже. `android init` настраивает CLI/agent environment и может установить `android-cli` в пользовательские каталоги; **это не доказывает project-local установку**. Проверять фактические пути, сообщённые CLI.

```powershell
android --version
android init
android skills list --long
android skills add --agent=codex --project=. android-cli
android skills add --agent=codex --project=. navigation-3
android skills add --agent=codex --project=. testing-setup
android skills add --agent=codex --project=. edge-to-edge
git status --short
```

Последние четыре команды — **пример для проекта, которому действительно нужны** CLI, Navigation 3, стратегия тестирования и edge-to-edge. ID проверены в Android CLI `1.0.16500706` (8 октября 2026 года); в новом окружении сначала сверить их через `android skills list`, а при другой архитектуре убрать нерелевантное. Не использовать `--all`, не ставить CameraX/Billing/ML Kit/R8 и прочее без задачи. Если `android-cli` уже установлен глобально, решить, нужна ли ещё и project-local копия для воспроизводимости команды; `skills add` может обновить существующий skill. Не редактировать официальные папки вручную: повторная установка способна перезаписать изменения. [Android описывает установку по ID и обновление](https://developer.android.com/tools/agents/android-skills); [параметры `--agent` и `--project`](https://developer.android.com/tools/agents/android-cli/commands/skills_add).

В Handbook Audio CLI создал [`/.agents/skills/android-cli/`](https://github.com/khodorkin-dmitrii/android-handbook-audio/tree/f93c5c796a88d237c27c8c08fca2f91d8b4e5d16/.agents/skills/android-cli), [`navigation-3/`](https://github.com/khodorkin-dmitrii/android-handbook-audio/tree/f93c5c796a88d237c27c8c08fca2f91d8b4e5d16/.agents/skills/navigation-3), [`testing-setup/`](https://github.com/khodorkin-dmitrii/android-handbook-audio/tree/f93c5c796a88d237c27c8c08fca2f91d8b4e5d16/.agents/skills/testing-setup) и [`edge-to-edge/`](https://github.com/khodorkin-dmitrii/android-handbook-audio/tree/f93c5c796a88d237c27c8c08fca2f91d8b4e5d16/.agents/skills/edge-to-edge). Отдельно существует **пользовательский**, не официальный [`skills/android-launcher-icons/SKILL.md`](https://github.com/khodorkin-dmitrii/android-handbook-audio/blob/f93c5c796a88d237c27c8c08fca2f91d8b4e5d16/skills/android-launcher-icons/SKILL.md); переносить его только для аналогичной задачи и отдельно от папок Android CLI. Проверить `SKILL.md` в каждой установленной папке, `git status` и обнаружение skills в новой сессии Codex. Локальные project skills и корневой `AGENTS.md` — разные механизмы: первый хранит специализированный workflow, второй — правила всего репозитория. См. также [пример организации repo-local skills в Codex](https://developers.openai.com/blog/skills-agents-sdk).

## 2. Базовая архитектура UI

Для нового проекта достаточно `Activity → Theme → Navigation host → Screen`. Каждый экран принимает неизменяемое состояние и явные callbacks; ViewModel собирает `StateFlow<UiState>`, а Activity/корневой host владеет общей навигацией и состоянием, которое переживает экран. Избегать прямого доступа Composable к сетевому DTO, Media3 и DataStore. Пример границ: [`MainActivity`][activity], [`AndroidHandbookAudioNavHost`][navigation], [`PlayerViewModel`][player-vm], [`PlayerUiState`][player-state].

Если используется Navigation 3, брать типизированные `@Serializable NavKey`, передавать через ключ **стабильный ID**, а модель загружать через ViewModel/repository. В [навигационном host][navigation] back stack принадлежит одному месту, `NavDisplay` описывает экраны, `pushIfNotTop` не допускает двух одинаковых верхних destination, `popIfTop` защищает повторный Back. `dropUnlessResumed` отсекает события click из уже уходящего экрана. Не строить второй Navigator и не переносить строковые route-паттерны Navigation 2. Это локальная защита от двойного tap, а не повод создавать универсальный navigation framework.

Общую панель поверх нескольких экранов располагать **вне** отдельных destinations. Здесь `MiniPlayer` находится в `bottomBar` внешнего `Scaffold` и отображается только на Playlists при наличии текущего медиа; на TrackList и Player он скрыт. Политика видимости отделена от самого компонента (`shouldShowMiniPlayer`). Для другого продукта заменить условия, но оставить один явный владелец overlay и его insets.

## 3. UI-решения, которые можно переиспользовать

| Решение | Как устроено здесь | Когда переносить |
| --- | --- | --- |
| Edge-to-edge без слоёного фона | `enableEdgeToEdge()` в Activity; непрозрачный root-фон под прозрачным внешним `Scaffold`; прозрачные экраны и `TopAppBar`. Внешний `Scaffold` отключает собственные `contentWindowInsets`, отдаёт контенту `outerPadding` и `consumeWindowInsets`; `MiniPlayer` отдельно получает `navigationBarsPadding()` — [host][navigation], [theme][theme]. | Если приложение рисует под system bars или имеет общую нижнюю панель. На каждом уровне явно решить, **кто** потребляет inset; не суммировать `safeDrawing`, `systemBarsPadding`, `navigationBarsPadding` и `Scaffold` padding без проверки. См. [официальное руководство по insets](https://developer.android.com/develop/ui/compose/system/insets-ui). |
| Скроллируемый список под `TopAppBar` | В [PlaylistsScreen][playlists] и [TrackListScreen][tracks] `LazyColumn` отодвинута на `contentPadding.calculateTopPadding()`, а внутренний `contentPadding` оставляет комфортные 16 dp. Нижняя часть учитывает padding Scaffold. | Для списков со статическим прозрачным TopAppBar. Проверить первый и последний элемент, жестовую и трёхкнопочную навигацию, появление нижней панели. |
| Карточка со стабильной высотой и мягким выделением | В [TrackCard][tracks] нет отдельной строки «Playing»: активная карточка меняет tint (`primaryContainer`, alpha `0.48f`), обычная использует `surfaceContainerHigh`, alpha `0.52f`. Состояния Play/Pause/Buffering/Error отражает `FilledIconButton` с иконкой и `contentDescription`. | Для интерактивных списков, где дополнительный статус не должен сдвигать элементы. Значения alpha — **настройка этого дизайна**, не норматив. Проверять контраст в светлой/тёмной теме. |
| Разные действия карточки и кнопки | `dispatchTrackItemClick`: клик по телу текущего трека открывает Player; по телу другого сначала использует тот же playback-start путь и затем открывает Player; кнопка только управляет воспроизведением. | Когда элемент имеет как переход, так и локальное действие. Не вкладывать одну общую кликабельную область поверх кнопки; отдельно проверять, что child click не вызывает parent click. |
| Автопрокрутка к текущему объекту | [TrackListScreen][tracks] ждёт первую реальную разметку `LazyColumn` и вызывает `animateScrollToItem` **только если** текущий элемент вне видимой области; одна попытка на вход. | Для «продолжить с места» в длинных списках. Не перехватывать пользовательскую прокрутку при каждом обновлении playback state. |
| Компактный MiniPlayer | [MiniPlayer][mini] показывает track/language, время `позиция / длительность` только при доступной duration (иначе duration либо ничего), иконки Play/Pause/Retry/Buffering. Прогресс-линия сверху. Текст берёт `MaterialTheme.colorScheme.onSurface`. | Для медиа-приложения с продолжением воспроизведения на других экранах; сам playback-controller остаётся вне UI. |
| Seek без видимого thumb | [AudioSeekBar][seek] использует `Slider` с пустым thumb, а высота дорожки анимируется `6.dp → 8.dp` на press/drag. В [PlayerControls][player-screen] позиция анимируется между обычными обновлениями, но во время жеста следует пальцу; отдельное preview-состояние удерживается до подтверждения фактической позиции. | Для медиа-прогресса. Сохранять доступную область касания шире визуальной линии; не анимировать значение против движения пальца. |
| Компактная скорость и язык | В [PlayerControls][player-screen] 2 языка — `SingleChoiceSegmentedButtonRow`; больше — горизонтально прокручиваемые chips. Скорости — `FilterChip` в горизонтально прокручиваемом `Row` с центрированием, если есть свободная ширина. | Если вариантов мало, но экран может быть узким. Проверять самый узкий поддерживаемый viewport: центрирование не должно отключать scroll. |
| Стабильный Player с/без транскрипта | [ActivePlayer][player-screen] использует `hasTranscriptPanel` из метаданных текущего трека, а не только текущий `Loading/Content`. В portrait: controls сверху, transcript снизу; в landscape: две колонки 50/50. **Без транскрипта** controls остаются под TopAppBar, без пустой второй колонки. | Если асинхронная панель не должна перестраивать весь экран при загрузке или смене языка. Условие двухпанельности брать из устойчивой domain metadata, а не из промежуточного network state. |
| Спокойная смена языка | [PlayerControls][player-screen] сохраняет последнюю известную duration текущего track и анимирует тексты/прогресс; [TranscriptPanel][player-screen] удерживает предыдущие cues, плавно меняет текст и показывает Loading только после 1 с. ViewModel связывает transcript с конкретным source, чтобы не показать данные другого языка — [PlayerViewModel][player-vm]. | Если новый контент быстро подменяется асинхронно. Не анимировать изменение структуры экрана, когда достаточно crossfade внутри фиксированных областей. Во время loading старые cues не должны оставаться кликабельными как актуальные. |
| Ambient-подложка и декоративный прогресс | [PlayerAmbientBackground][ambient] рисует три медленно движущихся radial-gradient blob и путь по закруглённому периметру. Путь начинается на «12 часах» и там же заканчивается при 100%; `progressKey` сбрасывает анимацию при смене трека. Обычные обновления сглажены, большие seek-прыжки быстрее, gesture preview ещё быстрее. | Только когда фон действительно поддерживает смысл экрана. Это декоративный индикатор, не замена доступному seek bar. Размещать позади прозрачных UI-слоёв, иначе линия исчезнет под нижней панелью. |
| Анимация переключения темы | [ThemeModeAction][theme-action] передаёт координаты кнопки; [ThemeRevealTransition][theme-reveal] захватывает предыдущий frame, синхронизирует смену темы и открывает новый экран круговой маской. [Theme][theme] обновляет системные bar styles в `SideEffect`, [AppThemeViewModel][theme-vm] меняет mode в памяти сразу, затем сохраняет в DataStore. | Опциональное усложнение. Вначале добиться **безмигающей** обычной смены темы, затем добавлять snapshot/reveal только при явной дизайн-задаче. |

## 4. UI/UX ошибки, уже встречавшиеся здесь

Это **регрессионный чек-лист**, а не список проблем текущей версии.

1. **Список виден под TopAppBar; первый/последний элемент обрезан.** Причина — прозрачный бар без согласованного `Scaffold` padding. Разделить внешние system insets и внутренний scroll content padding; проверить верх/низ на реальном устройстве и обеих навигационных схемах. Пример — [PlaylistsScreen][playlists] и [TrackListScreen][tracks].
2. **Зазор между списком и MiniPlayer либо линия фона обрывается перед ним.** Обычно конфликт `bottomBar` padding, нижнего `contentPadding` списка, непрозрачной поверхности или лишнего контейнера. Проверять итоговую геометрию обеих областей; фон должен рисоваться под всей общей оболочкой, а панель иметь прозрачный/полупрозрачный container. См. [host][navigation] и [MiniPlayer][mini].
3. **Полупрозрачные карточки показывают внутренние прямоугольные границы после добавления тени.** Несогласованные shape, clip, shadow и вложенный фон проявляются через alpha. Проверять весь стек модификаторов и Material `Card` на светлой/тёмной подложке; не добавлять elevation механически. См. [TrackCard][tracks].
4. **Состояние «Playing» увеличивает высоту только одного элемента.** Это дёргает список. Использовать tint/иконку/семантику в существующих местах, а не дополнительную строку. При изменении языка, времени и title не допускать неограниченной высоты карточки.
5. **Текст MiniPlayer остаётся тёмным после смены темы.** Причина — фиксированный цвет или неверный `LocalContentColor` при полупрозрачном `Card`. Для текста явно брать подходящие `MaterialTheme.colorScheme.onSurface`/`onSurfaceVariant` и проверять контраст обеих тем — [MiniPlayer][mini].
6. **Быстрый двойной tap открывает два одинаковых экрана; Back уходит на два уровня.** Одной защиты на кнопке недостаточно: lifecycle gate (`dropUnlessResumed`) плюс проверка верхнего `NavKey` на push/pop — [navigation][navigation].
7. **Смена темы даёт серый кадр.** Это был не только splash: прозрачные Scaffold/TopAppBar успевали показывать root/window background, а новый theme frame и системные бары менялись неатомарно. Нужен надёжный root background и согласованная смена темы; snapshot reveal в [ThemeRevealTransition][theme-reveal] решает именно визуальный переход. Не маскировать ошибку случайным `delay`.
8. **При переключении языка Player «подпрыгивает».** Нельзя строить `TranscriptPanel` по временному `Loading` и терять duration на период загрузки новой rendition. Устойчивая структура — по `hasTranscriptPanel` из metadata; текущая duration сохраняется до новой; внутри фиксированных зон текст меняется анимированно — [PlayerUiState][player-state], [PlayerControls][player-screen].
9. **В landscape без транскрипта controls оказываются под TopAppBar.** У двухколоночного режима должно быть явное условие `hasTranscriptPanel && isLandscape`, а no-transcript layout должен начинаться с `Scaffold` content padding — [ActivePlayer][player-screen].
10. **Декоративная линия двигается дискретно или отстаёт от ручного seek.** Обновлять фон от того же progress/preview, что и controls; для жеста применять короткую анимацию, для обычного хода — более длинную. `progressKey` не должен смешивать прогресс разных треков — [PlayerScreen][player-screen], [PlayerAmbientBackground][ambient].
11. **Восстановленный после холодного старта MiniPlayer открывает Player без доступных next/previous и языка.** Playback bookmark сам по себе не содержит весь playlist context. После восстановления дозагрузить manifest и передать порядок треков playback-controller без требования сначала открыть TrackList — [PlayerViewModel][player-vm]. Для нового приложения это пример общего правила: восстановленный UI должен получить все необходимые зависимости, а не только отображаемый ID.

## 5. Минимальная проверка перед UI-polish

- Пройти Playlists → TrackList → Player → Back, повторить быстрые двойные taps; проверить, что кнопка внутри карточки не навигирует.
- Проверить cold start с восстановленным состоянием, отсутствие медиа, buffering/error, неизвестную duration, очень длинные title, один/несколько языков.
- Проверить portrait/landscape, с/без транскрипта, light/dark/system, узкий экран, gesture navigation и 3-button navigation. Переключать тему и язык во время воспроизведения и паузы.
- Проверить seek во время drag и после отпускания: фактический прогресс, декоративный прогресс и время должны сходиться без скачка назад.
- Для логики добавить целевые JVM unit tests (navigation guards, click dispatch, state mapping, recovery, parser). Не увеличивать число тестов ради числа; screenshot/golden tests не обязательны для такого старта. Примеры: [navigation tests][nav-test], [track interaction tests][track-test], [player state tests][player-test].
- После значимого изменения кода: `./gradlew testDebugUnitTest assembleDebug lintDebug`, затем `git diff --check`. Для чисто документационного изменения достаточно проверки ссылок и `git diff --check`.
