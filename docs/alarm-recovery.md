# Schedule recovery (Step 7B)

Room's explicitly enabled alarm definition and pending occurrence IDs are the source of truth. `OneShotAlarmCoordinator.reconcile()` is the single recovery entry point and uses the same mutex as Save, disable/delete, snooze, delivery, and dismissal. A repeated pass keeps the same occurrence identity if its meaning has not changed. It re-arms the same `PendingIntent` even on foreground entry (also repairing a lost platform entry after force-stop and relaunch); AlarmManager replaces rather than duplicates the platform alarm.

Reconciliation runs after `BOOT_COMPLETED` (after first unlock), `MY_PACKAGE_REPLACED`, `TIME_SET`, `TIMEZONE_CHANGED`, exact-alarm grant, and foreground entry. The manifest receiver uses bounded `goAsync()` work; no activity or recovery service is started by these broadcasts. Existing unscheduled legacy recurring rules remain dormant until the user explicitly saves/enables them. Disabled, completed, and missed one-shots are not reactivated. Notification and full-screen access are separate from exact-alarm scheduling; missing exact access leaves configured intent and displays a blocked state.

Regular recurring alarms recompute their next selected weekday in the current device zone, using the existing DST gap/overlap policy. The last accepted regular instant is a lower bound, so rolling the clock backward cannot replay a consumed occurrence. The pending occurrence is replaced only when its instant changes or becomes overdue; overdue regular occurrences are skipped and the next future day is scheduled. One-shots retain their saved concrete instant across clock/time-zone changes. If it is overdue during recovery, it is marked `MISSED` and disabled, never moved to tomorrow. An accepted ringing occurrence is not confused with an overdue pending occurrence. Step 7C persists its original five-minute elapsed-realtime deadline: within the same boot, a restarted service may continue only for the remaining time; after the deadline it completes without a new ring. A previous-boot ringing session ends rather than restarting. Pre-7C ringing rows without a verifiable deadline are ended conservatively. Foreground reconciliation may restart only a still-valid interrupted ring and never resets its deadline.

Step 7C also keeps an explicit enabled Save recoverable if the process dies before platform scheduling finishes. A failed foreground-service start or audio startup is recorded on the alarm instead of leaving a permanent ringing state; the alarm list shows the failure. A second occurrence accepted during a valid ring is skipped, while its recurring rule still advances. Dismiss is persisted before the player stops; the service watches the occurrence identity and releases playback/asset-use protection when Save, disable, delete, Dismiss or Snooze invalidates it. These changes use Room migration 5→6 for a nullable ringing deadline and failure message; no stored alarms or audio are removed.

Snooze is separate from the recurring schedule. In one boot it uses `setExactAndAllowWhileIdle(ELAPSED_REALTIME_WAKEUP)`, preserving the five-minute deadline across wall-clock changes. Room stores the elapsed deadline, Android boot count, and wall-clock recovery instant. Across reboot the old elapsed value is discarded, the remaining wall-clock duration is converted to a new elapsed deadline, and an overdue snooze expires without ringing. If the system boot count is unavailable, recovery conservatively uses the wall-clock instant rather than reusing an unverified elapsed deadline. Android may still delay `setExactAndAllowWhileIdle` delivery under idle-mode quotas; this is a platform limitation of the elapsed-time approach, not a guarantee of second-level precision. An already completed or cancelled occurrence has no pending identity and cannot be recreated. Revoking exact-alarm access can cancel platform entries without a revocation broadcast; foreground entry detects the loss, and the grant broadcast/next foreground entry re-arms eligible future entries.

This is **after-first-unlock** recovery only: Room and audio stay in credential-encrypted storage, with no Direct Boot copy. Alarms due before first unlock are not supported. Force-stop also suppresses broadcasts/alarms until the user launches the app; the app does not claim otherwise. Receiver work is capped at eight seconds; if interrupted, the next foreground/system recovery pass resumes idempotently. There is no periodic polling.

Platform references (target SDK 37): [implicit broadcast exceptions](https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions), [Direct Boot](https://developer.android.com/privacy-and-security/direct-boot), [BroadcastReceiver time limits](https://developer.android.com/reference/android/content/BroadcastReceiver), [AlarmManager and exact-alarm grant](https://developer.android.com/reference/android/app/AlarmManager), [exact-alarm access](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms).

Foreground-service restart policy follows Android's [Service redelivery contract](https://developer.android.com/reference/android/app/Service#START_REDELIVER_INTENT); an exact alarm and a user notification action are documented [background-start exceptions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start). Neither exception guarantees success, so failures remain visible/recoverable. No protection is claimed for force-stop or for delivery before first unlock.
